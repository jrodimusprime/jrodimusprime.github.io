Executive overview

Subagents that share one copy of their data on one machine hand off a 1 GiB file 3 to 50 times faster than through any network store, without leaving AgentCore governance.

Example. An orchestrator fans a 1 GB data room out to subagents that extract clauses, check financials and flag risks; the data changes hands 10 times. With 30 s of model time, the job takes 31 s with shared memory in one AgentCore session, 36 s via S3, 53 s via EFS and 88 s via Postgres.

Recommendations.

  • Keep every subagent an AgentCore runtime with its own identity and audit trail. This is the one fixed requirement.

  • Co-locate trusted subagents in one session and share data through memory.

  • Commit work in whole units, so no reader ever sees partial output.

  • Use S3 to cross machines or persist results, and databases for small records only.

Abstract

Co-locating AgentCore subagents on one Instances session and sharing a memory-mapped volume moves a 1 GiB file in about 0.12 s, 5.5 to 50 times faster than any networked alternative under representative constants.

The paper makes one hard assumption: every subagent runs under AgentCore orchestration, because its governance layer is required. Everything else is optimised within that constraint.

Subagents on Amazon Bedrock AgentCore often exchange multi-gigabyte files and coordinate on them with locks. We propose a zero-copy cell: subagent runtimes invoked with one session ID land on one EC2 instance and share an EBS volume through the kernel page cache. We prove that any cross-process share costs at least one cache-coherence transfer plus one pass over the bytes, and that the cell meets this bound once mappings are reused.

We compare the cell against five baselines: copy-based local I/O, SQLite in WAL mode, an NFS mount (EFS or S3 Files), Amazon RDS for PostgreSQL and S3 objects. The baselines rank differently by size: S3 overtakes NFS above about 61 MB and SQLite above about 100 MB. Databases are competitive only for small locked commits. All constants are representative, not measured; Section 8 gives the benchmark needed to replace them.

1. Introduction

Where a shared file lives relative to compute decides how fast subagents can hand it to each other, and the gap spans five orders of magnitude.

Multi-agent systems fan work out to subagents that produce large intermediate artifacts: datasets, embeddings, code trees, model checkpoints, rendered media. Other subagents consume those artifacts, often concurrently, and some must update them under a lock. The default choice is whatever storage the team already runs: an object store, a shared filesystem or a database.

That default is rarely examined. A file in the consumer's own address space costs nothing to share. The same file behind a network round trip and a server process costs milliseconds before the first byte moves, and a per-client bandwidth cap after that.

This paper makes four contributions:

  1. A taxonomy of sharing mechanisms ordered by distance from compute.

  2. The zero-copy cell, a concrete design for AgentCore Runtime Instances.

  3. A cost model with three results: a lower bound, a dominance ordering and closed-form crossover sizes.

  4. A representative evaluation, a decision matrix and a benchmark protocol for replacing representative constants with measurements.

Scope: the one hard assumption

Every subagent must run as an AgentCore runtime, invoked through AgentCore, so that it sits inside AgentCore's governance layer. This is the paper's only hard assumption; the question is how to make file sharing fast without leaving that layer.

The assumption has three consequences for the design space:

  1. Each subagent keeps its own identity and audit trail. Each agent runs with IAM credentials from its own runtime's execution role, and CloudTrail records the principal and session ID of every invocation (security model).

  2. Collapsing subagents into one process is out. Threads in one runtime (mechanism A) would merge identities and audit records, so A is kept only as a theoretical bound.

  3. Placement follows AgentCore's rules. Co-location is available only on the Instances compute type, by sharing a session ID, and the session is the trust boundary.

Because each governed subagent is a separate process, Theorem 1's cross-process bound applies, and Corollary 1 makes the zero-copy cell the fastest admissible design.

2. Background: AgentCore storage and placement

AgentCore's Instances compute type is what makes the cell possible: runtimes invoked with the same session ID run on the same EC2 instance and can mount the same EBS volume.

On Instances, invoking a second runtime that shares the capacity provider with the same runtimeSessionId launches it beside the first. If both runtimes list the same capacityProviderVolume, both mount it (file system configurations).

On microVMs, sharing across sessions requires a bring-your-own mount. EFS offers full POSIX with advisory locking and close-to-open consistency over NFSv4.1. S3 Files mounts over NFSv4.2 and syncs bidirectionally with a bucket, with roughly 60 seconds of batching before NFS writes appear through the S3 API (S3 Files guide).

The trust boundary is the session. Agents on one instance are not isolated from each other, so only mutually trusted subagents may share a cell (security model).

3. The proposed design and the baselines

We propose two mechanisms and compare them against five baselines that teams commonly reach for; the baselines are not recommendations.

Each container a mechanism sits in adds a cost to everything inside it: a copy at the instance level, a network round trip in the VPC, a service request in the Region.

Proposed

A. Threads in one process. All subagents run as threads or coroutines in one agent runtime. Sharing a file is passing a pointer. A is the theoretical upper bound, but one process means one failure domain and one IAM identity, so it bypasses per-subagent governance and is not admissible under the paper's hard assumption.

B. Zero-copy cell. Each subagent is its own runtime on one capacity provider, invoked with one session ID, mounting one EBS volume. The volume holds three regions:

  1. A control file every agent maps with MAP_SHARED, holding robust process-shared futexes, generation counters, leases with fencing tokens and an event ring buffer.

  2. A chunk store of immutable, content-addressed chunks of 16 to 64 MiB. Readers map sealed chunks without locks. Writers filling a chunk take OFD byte-range locks, which the kernel releases if the holder dies.

  3. Manifests listing a file's chunks and generation, committed by atomic rename so readers always see a complete version.

Baselines

C. Copy I/O, co-located. The same cell, but consumers read() bytes into private buffers. It isolates the cost of copying.

D. SQLite in WAL mode, co-located. Files stored as blobs in a SQLite database on the shared volume. WAL needs shared memory, so all processes must be on one host and it does not work over a network filesystem (SQLite WAL). Containers on one host sharing a volume do satisfy this (Willison, 2026).

E. NFS mount. EFS or S3 Files mounted into microVM sessions in the same Availability Zone, with advisory locks over NFS.

F. Amazon RDS for PostgreSQL. Files stored as bytea or large objects in a same-AZ instance, with row locks for coordination.

G. S3 objects. Producers PUT, consumers GET with parallel ranged requests, and manifests commit with conditional writes.

Reference architecture of the cell

The cell keeps every byte on one instance and touches the network only to seed the volume and to persist sealed results.

  1. The caller invokes each subagent runtime with the same runtimeSessionId, which names the cell.

  2. AgentCore Runtime launches every runtime that shares the capacity provider on the same managed EC2 instance, each with its own execution role.

  3. Runtimes share bytes through the kernel page cache: mapped chunks, futexes in the control file and OFD byte-range locks.

  4. The capacity provider volume holds the control file, chunk store and manifests, and survives session stops.

  5. Sealed chunks and manifests spill asynchronously to S3 through a gateway endpoint, committed with conditional writes, so other cells can read them.

  6. An EBS snapshot named in the capacity provider seeds the volume with reference data at first launch.

Atomic units of work

Every unit of work should commit all-or-nothing, on a boundary chosen on purpose and at a size chosen from the cost model.

We borrow the vocabulary of atomic design: atoms compose into molecules, molecules into organisms. Here each level is also atomic in the transactional sense, so a reader never sees part of a unit.

A crash at any level leaves the committed level below intact and the level above unchanged, so recovery is discarding what never committed.

Three rules.

  1. Intentional boundaries. An atom ends at a semantic unit (a record, a shard, a function, a tool-call output) and preserves a stated invariant. A byte count caps an atom's size; it never defines where the atom ends, because a cut mid-record exposes half a fact.

  2. Compose only committed parts. A manifest references only sealed atoms, and a task commit references only committed manifests.

  3. Idempotent identity. An atom's ID is the hash of its content, so a deterministic retry produces the same atom and deduplicates. A non-deterministic retry produces a different hash, so manifests commit conditionally and the first commit wins; losing atoms are garbage-collected.

Sizing an atom. Small atoms pay a fixed seal cost λ_u many times; large atoms lose more work when a writer fails mid-atom. With producer rate β_p and failure rate φ per second of production, the expected overhead of producing S bytes in atoms of size c is

O(c) = \frac{S}{c}\,\lambda_u + \varphi \, \frac{S}{\beta_p} \cdot \frac{c}{2\beta_p}

Setting dO/dc = 0 gives the optimal atom size, the same square-root form as Young's optimal checkpoint interval:

c^{*} = \beta_p \sqrt{\frac{2\lambda_u}{\varphi}}

Worked example. With β_p = 100 MB/s, λ_u = 50 µs and one failure per hour (φ = 2.78 × 10⁻⁴ per second): c* = 100 MB/s × √(2 × 5 × 10⁻⁵ / 2.78 × 10⁻⁴) = 100 MB/s × √0.36 = 60 MB, so 64 MiB chunks. Ten times the failure rate shrinks c* by √10, to 19 MB.

Generative atoms. When a subagent generates output with a model, an atom's size and boundary are not known in advance, so sizing must be controlled at run time rather than fixed. The controller in Figure 3 does four things:

  1. Seals on the first of three triggers: size reaches c*, the generator emits a semantic boundary, or a time budget T_max elapses. Setting T_max = c* / β̂_p makes the size and time triggers agree in steady state, and bounds lost work to T_max of generation.

  2. Makes boundaries intentional. The generator is constrained to structured output with explicit boundary markers, so semantic boundaries arrive more often than c*. If they don't, the controller falls back to the time budget and flags the unit for review.

  3. Retunes online. It keeps moving averages φ̂ and β̂_p, recomputes c* from the formula above, and clamps it to a fixed range so it doesn't oscillate.

  4. Never half-commits. Each open atom holds a lease with a fencing token and a heartbeat. If the lease expires, the atom is discarded, and a stale writer's late seal is rejected by its token. A cap on open atoms per subagent keeps uncommitted bytes from crowding the page cache.

4. Cost model

Every mechanism is reduced to three numbers: a fixed latency, a per-byte cost to move the data, and a per-byte cost to read it that all mechanisms share.

Bulk workload. One producer shares a file of S bytes with N consumers, and each consumer reads every byte. The producer's own work to generate the bytes is common to all mechanisms and excluded. We count only the cost of getting bytes from where they were produced to where they are read. For one consumer:

T_k(S) = \lambda_k + S\left(\frac{1}{\beta^{w}_k} + \frac{1}{\beta^{r}_k}\right) + \frac{S}{B_{mem}}

Here λ_k is the fixed synchronization and setup latency, β^w_k and β^r_k are the effective write and read transfer bandwidths, and S / B_mem is the consumer touching the bytes in RAM. We write c_k = 1/β^w_k + 1/β^r_k for the per-byte transfer cost, so T_k(S) = λ_k + c_k S + S / B_mem.

Small-op workload. One subagent takes a lock, reads and rewrites a 4 KiB record, and releases the lock. This models claiming a task or bumping a manifest generation.

Hardware constants (common to all). B_mem = 10 GB/s single-core read bandwidth; B_copy = 8 GB/s memcpy; fault-around window F = 64 KiB; minor fault t_f = 0.5 µs; syscall t_sys = 1 µs; read buffer b = 1 MiB. GB means 10^9 bytes.

5. Theoretical results

The cell is provably as fast as any cross-process scheme can be, up to a mapping cost that vanishes with reuse, and no baseline can beat copy I/O on the same host.

Theorem 1 (lower bound)

Any scheme in which a consumer in a different thread or process from the producer reads all S bytes takes at least

T \geq t_c + \frac{S}{B_{mem}}

where t_c is the minimum inter-core cache-coherence latency.

Proof. The consumer must touch all S bytes, which costs at least S / B_mem. It must also learn the bytes are ready, which means observing a write made on another core; that costs at least one coherence transfer, t_c. The consumer cannot safely read before the signal arrives, so the two costs are sequential. ∎

Corollary 1. Mechanism A attains t_c + S / B_mem and is optimal within the model. Mechanism B adds a mapping cost amortized over R shares:

T_B(S) - T_A(S) = \frac{\lceil S/F \rceil \, t_f}{R} \;\xrightarrow{R \to \infty}\; 0

So B is asymptotically optimal among cross-process schemes. For S = 1 GiB the mapping cost is 16,384 × 0.5 µs = 8.2 ms at R = 1, and 0.08 ms at R = 100.

Theorem 2 (dominance)

For every S ≥ 0: T_A ≤ T_B ≤ T_C, and T_C ≤ T_k for every k in {D, E, F, G}.

Proof. Let O_k be the multiset of operations on mechanism k's critical path, each with non-negative cost. If O_j ⊆ O_k then T_j ≤ T_k. The inclusions are:

  • O_B = O_A ∪ {page faults, futex in a shared mapping}.

  • O_C = O_B ∪ {syscalls, kernel-to-user copies}. A real read() also faults pages into the page cache, so it contains O_B's work.

  • O_D ⊇ O_C: SQLite reads and writes pages through the same copy path, plus B-tree traversal, WAL appends and checkpoint copies.

  • O_E, O_F, O_G ⊇ O_C: each delivers bytes into a user buffer by copy, plus network round trips and server-side processing.

Each added operation has positive cost in practice, so every inequality is strict. ∎

Theorem 2 is a partial order. It does not rank D, E, F and G against each other, because their operation sets are not nested.

Theorem 3 (crossover size)

For two baselines a and b with λ_a < λ_b and c_a > c_b, a is faster below and b faster above

S^{*}_{a,b} = \frac{\lambda_b - \lambda_a}{c_a - c_b}

Proof. T_a(S) − T_b(S) = (λ_a − λ_b) + (c_a − c_b) S, since the S / B_mem terms cancel. This is linear in S with a negative intercept and positive slope, so it has exactly one root, at S*. ∎

If λ_a ≤ λ_b and c_a ≤ c_b, a dominates b at every size. Under Section 4's constants, SQLite dominates both NFS and RDS, and NFS dominates RDS above about 30 KB. The crossovers against S3 are worked in Section 6.

7. Discussion and decision matrix

Use the cell when subagents trust each other and share large data, S3 to cross cells, and databases for metadata rather than bytes.

When storage choice matters

If file sharing is a fraction f of a task's end-to-end time, no storage design can speed the task up by more than

\text{speedup} \leq \frac{1}{1 - f}

The storage result matters only where f is large, which is why the paper should report f for real workloads.

With 30 s of inference, the cell keeps sharing near 4% of task time, while slower baselines make storage the dominant cost. The 30 s and ten shares are assumptions; replace them with measured values.

Recommended composition

  • Inside a cell: the zero-copy cell for bytes, with the control file (or SQLite on the shared volume) as the catalogue, and the atomic units of Section 3.

  • Across cells: S3 objects with conditional manifest commits; a sealed atom crosses the network once.

  • Databases: RDS for PostgreSQL only for relational task state that other systems query, holding S3 keys rather than file bytes.

  • Isolation first: an NFS mount when subagents must not share an instance, accepting a 2 ms floor per operation.

8. Threats to validity and benchmark protocol

The theorems hold for any constants; the numbers in Sections 6 and 7 do not, and must be replaced with measurements before publication.

Threats.

  • Representative constants. Every λ and β in Section 4 is an assumption. EBS, EFS and S3 limits change, and they vary by instance size and Region.

  • Warm caches. The model assumes bytes are in the page cache. A cold cell reads from EBS first, adding S / β_EBS to mechanisms A to D.

  • Client caching. NFS clients cache data and attributes, so repeat reads on E can beat the model while first reads match it.

  • Contention. The model has one writer. With many writers, SQLite serializes on one WAL writer, RDS on row locks, and S3 on per-prefix request rates.

  • Database tuning. SQLite synchronous mode, page size and mmap_size, and RDS instance class and storage type, can each move D and F by several times.

Protocol. Run each test on the AgentCore instance types you deploy, with all resources in one Availability Zone.

  1. Hardware constants: a futex and OFD-lock microbenchmark for t_c and lock cost; a memcpy test for B_mem and B_copy; page-fault timing for t_f.

  2. Volume: fio sequential and random reads and writes on the capacity provider volume, cold and warm.

  3. Each mechanism: the bulk workload at 4 KiB to 16 GiB in powers of four, and the small-op workload, with N = 1, 4 and 16 consumers.

  4. Statistics: at least 30 runs per point; report median and p99 with 95% bootstrap intervals.

  5. Fit λ_k and c_k per mechanism by least squares on T_k(S), then recompute the crossovers from Theorem 3 and report fitted against assumed values.

  6. Publish the harness, raw results and instance metadata so the numbers can be reproduced.

9. Conclusion

Given that every subagent must run under AgentCore governance, put trusted subagents in one cell, share bytes through the page cache, and reach for networked storage only to cross cells or persist results.

The zero-copy cell meets the cross-process lower bound once mappings are reused, and copy-based local I/O bounds every networked baseline from below. Among those baselines no single winner exists. S3 wins large transfers, SQLite wins small commits on one host, and RDS for PostgreSQL wins neither under these constants. The open question is empirical: the benchmark in Section 8 will fix the constants, and Theorem 3 will then give each deployment its own crossover sizes.

Appendix A. Designer-chosen versus agent-chosen atoms

Inside a cell, agents should choose which atom to work on themselves: in simulation, self-scheduling cuts load-imbalance overhead for generative work from 21.8 s to 2.6 s, and a fixed plan wins only once each claim costs more than 5 to 126 ms.

A.1 Two separate decisions

Choosing atoms involves two decisions that are often conflated:

  • Definition: what an atom is, meaning its boundary type, the invariant it preserves and its size envelope.

  • Assignment: which agent works on which atom, and when.

Either can be fixed by the designer before the run (static) or made by agents during it (dynamic). Section 3's rules govern definition. This appendix gives the evidence for assignment first, then returns to definition.

A.2 Static assignment: the designer's plan

The orchestrator splits k atoms evenly across n agents before the run. If atom durations have mean μ and standard deviation σ, each agent's load is a sum of m = k / n durations, and the run ends when the slowest agent finishes. A normal approximation to the maximum of n such sums gives the expected overhead above perfect balance:

\mathbb{E}[T_{\text{static}}] - \frac{W}{n} \approx \sigma \sqrt{m} \, \sqrt{2 \ln n}

The overhead grows with the variability of the work and with the square root of the atoms per agent. Model calls make variability high, because output length and endpoint latency vary from call to call.

A.3 Dynamic assignment: agents claim atoms

Each agent claims the next unclaimed atom when it finishes, through a locked claim costing δ. Graham's list-scheduling bound caps the imbalance at roughly one atom, and the claims add their own cost:

T_{\text{dynamic}} \leq \frac{W}{n} + \left(1 - \frac{1}{n}\right) t_{\max} + \frac{k}{n}\,\delta \qquad (k\delta \ll W/n)

The imbalance term no longer grows with m, but the claim term does. Dynamic assignment therefore wins whenever claims are cheap relative to the variability they absorb. The cell makes claims cheap: one claim is one locked commit in the control file, about 1 µs in Figure 5.

A.4 Simulation

We simulated both policies with n = 8 agents and k = 800 atoms of mean 2 s, so 200 s of work per agent. Durations were lognormal with a coefficient of variation of 0.75 (generative work, such as model calls) or 0.05 (uniform work, such as deterministic transforms). Claims were serialized through one lock, and each point is the mean of 300 runs.

For generative work, a fixed plan leaves 21.8 s of imbalance against 2.6 s for claiming in a cell. For uniform work the figures are 1.41 s and 0.87 s. The normal approximation in A.2 overestimates the static overhead (30.6 s and 2.0 s), as expected of an approximation to a maximum.

A.5 Agent-chosen boundaries

For generative work, the agent also decides where each atom ends. Adding claim cost and imbalance to Section 3's seal-versus-rework trade-off gives a per-agent overhead in time units, where τ is an atom's duration:

O(\tau) = \frac{W}{n\tau}\left(\lambda_u + \delta\right) + \tau + \varphi \, \frac{W}{n} \cdot \frac{\tau}{2}

The three terms are fixed costs per atom, imbalance of about one atom, and expected rework. Minimizing gives

\tau^{*} = \sqrt{\frac{(W/n)\,(\lambda_u + \delta)}{1 + \varphi W / (2n)}}

Worked values. With W / n = 200 s, λ_u = 50 µs and one failure per hour (so φW / 2n = 0.028), τ* is 0.10 s in a cell (δ = 1 µs), 0.77 s over NFS (δ = 3 ms) and 3.1 s over S3 (δ = 50 ms). In a cell, atoms can end at fine semantic boundaries chosen by the agent; over the network they must be seconds long, which favours coarse atoms fixed by the designer.

A.6 A division of responsibility

The evidence supports three regimes:

RegimeWho defines atomsWho assigns atomsUse when
Catalogue and claim (default)DesignerAgentsMost work inside a cell
Envelope and claimAgents, within a designer-set envelopeAgentsGenerative work whose boundaries emerge during the run
Fixed planDesignerDesignerUniform work with claims over about 5 ms, or a plan that must be approved before the run

In every regime the designer owns the invariant each atom preserves, the allowed boundary types, the size envelope [τ_min, τ_max] and which agents may claim. Agents own only the run-time choices inside those limits: which atom next, and where to cut within the envelope. This is what makes dynamic choice intentional rather than improvised.

Dynamic choice also stays inside the governance assumption. Every claim and seal is written to the control file with a fencing token and the claiming runtime's identity, then copied into the manifest. Together with AgentCore's record of each invocation, this reconstructs who worked on what and when.

A.7 Limits of the evidence

The simulation assumes independent durations, a single lock and no failures. Heavy-tailed durations would favour dynamic assignment further, while a correlated slowdown, such as a throttled model endpoint, hurts both policies alike. The next step is to replay measured atom durations from real subagents through the same simulation, following the protocol in Section 8.

All figures come from a representative cost model, not measurements. The cost model is in model/model.py and the scheduling simulation in model/schedule_sim.py; Section 8 describes the benchmark needed to replace its constants.
